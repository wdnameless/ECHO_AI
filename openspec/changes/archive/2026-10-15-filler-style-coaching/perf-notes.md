# Perf notes: «услышал → ответ» (R06, T6)

Источник: замер PerfMeasure на dev-сессии (Vite + CDP + рантайм metrics.ts/QuestionAssembler).
Оговорка: ASR-сайдкар и LLM-ключи в dev недоступны — их тайминги из эталонных бенчмарков Parakeet-TDT/Gemini Flash, остальное измерено динамически.

## Вклады (Interview, flushGap 450мс)

| Этап | С `?` | Без `?` |
|---|---|---|
| VAD тишина (silence_chunks=12) | 256мс (33%) | 256мс (21%) |
| ASR-финал | 65мс (8%) | 65мс (5%) |
| flushGap | 0мс (эмит сразу) | 450мс (36%) |
| JS dispatch | <3мс | <3мс |
| TTFT LLM | 432мс (58%) | 432мс (35%) |
| **Итого** | **~756мс** | **~1206мс** |

General-профиль (flushGap 1500мс): ~2256мс, доминирует flushGap (66%).

## Вывод: два узких места

1. **Без `?`: двойное ожидание тишины 706мс** (VAD 256 + flushGap 450) — больше, чем вся сеть+генерация.
2. **С `?`: сетевой TTFT 432мс** (58%) — вне нашего кода, лечится только выбором провайдера/модели.

## Резерв: маскировка задержки

Филлер сейчас приклеивается к первому токену LLM (`recordFirstToken`), а не показывается в момент `startQuestion`. Вывод плейсхолдера сразу при финализации вопроса срезал бы *воспринимаемую* задержку до ~0мс.

## Решение по T7 (точечный фикс, маленький scope)

1. Не снижать flushGap глобально (порвёт длинные реплики) — вместо этого **ранний эмит уже есть** (`immediateOnQuestionMark`, earlyEmit): проверить его покрытие повествовательных вопросов нельзя без ML-классификатора — НЕ делаем в этой задаче.
2. Делаем **маскировку**: показывать филлер/плейсхолдер в момент `startQuestion`, а не первого токена. Изменение локальное (useAIStreaming), эффект — главный на восприятие.
3. Документировать пользователю: вопросы с `?` отвечают за ~0.75с, без — за ~1.2с; General — за ~2.2с.
